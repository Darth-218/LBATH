# Research corpus

Structured extraction of papers adjacent to our LLM threat-hunting system.

## Why this exists

We need to justify design decisions against prior art, and we keep re-reading
the same papers. Free-form notes made comparison impossible because every set
of notes captured different things. This directory is the fix: one YAML file
per paper, validated against a schema, rendered into a comparison view.

## Layout

```
research/
    schema.json           # JSON Schema for all entry types
    papers/<id>.yaml      # objective extraction — reviewed against the paper
    notes/<id>.yaml       # relevance_to_us — reviewed as an argument
    curated_gaps.yaml     # curated cross-paper gaps
    archive/              # historical reports, not active corpus
    templates/            # copy-paste starters
    scripts/              # validate.py, render.py
    COMPARISON.md         # generated, committed
    GAPS.md               # generated, committed
    comparison.json       # generated, committed
```

Facts and opinions live in separate files because the paper's architecture
never changes, while our opinion of it changes every time our system does.
Cross-paper gaps live in `curated_gaps.yaml` because they do not belong to a
single paper. Colocating these would mean the record of the paper mutates for
unrelated reasons. Historical reports kept for provenance go in `archive/` and
are not validated as corpus entries.

## Adding a paper

```sh
pip install -r research/requirements.txt
```

1. **Check it is not already here.** Search `papers/` by title and by
   identifier (arXiv id, DOI, or URL) before you start.
2. Pick the id prefix — `arxiv-`, `doi-`, `url-`, or `todo-` — per
   [CONVENTIONS.md](CONVENTIONS.md). Copy `templates/paper.yaml` to
   `papers/<id>.yaml`. The filename stem must equal the `id` field; for `doi-…`
   and `url-…` ids, replace `/` with `_` in the stem.
3. Copy `templates/note.yaml` to `notes/<id>.yaml` using the same `<id>`.
4. Fill both in. Cite section, table, or figure numbers where a claim comes
   from the paper.
5. `python research/scripts/validate.py` — must print `ok`.
6. `python research/scripts/render.py`
7. Commit both new YAML files plus the regenerated `COMPARISON.md`,
   `GAPS.md`, and `comparison.json`.
8. Open the PR.

CI runs `validate.py` and `render.py --check` on any PR touching `research/`.
Green means the entry is structurally sound and the generated files match
their source. It does not mean the extraction is correct — only a reviewer
reading the paper can establish that.

## Adding a curated gap

1. Copy the shape in `templates/curated_gaps.yaml` into `curated_gaps.yaml`.
   Use a stable `gap-…` id and write the gap as a cross-paper claim.
2. Choose `status: open` when current entries support the claim. Use
   `status: historical` when the source is not in the corpus, and record where
   the claim came from in `origin`.
3. Add evidence entries that point at real paper or note fields. Each `quote`
   must match the referenced field verbatim.
4. Run `validate.py` and `render.py`, then commit `curated_gaps.yaml` with the
   regenerated `GAPS.md` and `comparison.json`.

## Conventions

Field definitions, enum tie-breaks, the `unknown` rule, relation vocabulary,
gap vocabulary, and the schema-change policy live in
**[CONVENTIONS.md](CONVENTIONS.md)**. Read it before your first entry.

## Generated files

`COMPARISON.md`, `GAPS.md`, and `comparison.json` are generated by `render.py`
and committed, lockfile-style: the PR diff shows what your paper changed about
the global picture, and `git blame` tells you when a row entered the corpus.
All three are marked `linguist-generated` so they collapse in diffs.

CI runs `render.py --check` and fails if either file is stale. Run
`render.py` locally before pushing, the same way you would run a formatter.

If merge conflicts on these files ever become frequent, switch them to build
artifacts — the migration is deleting the files and adding a publish step.
